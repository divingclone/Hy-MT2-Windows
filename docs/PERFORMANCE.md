## 当前程序：官方 llama.cpp、F16 KV 与 Q8 KV

2026-09-18 使用当前程序和默认模型重新测试 README 的三种方案，每项三次。沿用原表的 64 条素材 × 8 轮，共 512 条请求、256 并发、每条上下文 1024、最大生成 512、batch/ubatch 2048、8 个推理线程。三轮顺序为官方/F16/Q8、Q8/官方/F16、F16/Q8/官方；每次新进程，没有单独预热请求。速度和显存来自同一批九次运行。

## 模型选择实验：公开语料、随机长短请求与 Q8 内核

2026-09-18 使用固定版本的 [OPUS-100](https://huggingface.co/datasets/Helsinki-NLP/opus-100) 中英平行语料重新验证。validation 生成 256 条校准文本，test 生成 256 条独立请求；每个长度组内两个翻译方向均衡，跨集规范化文本重复为零。单句、2–6 句及 7–16 句组合占 50% / 25% / 25%，原顺序随机混合，不重复同一句填充长度。组合不是连贯原始篇章，也不是生产流量或完整官方 OPUS 分数。

所有推理保留 **4096 上下文、2048 最大生成**，不按参考译文长度修改预算。实际 prompt 长度为 28–687 token（P50=75、P95=391）；32 并发全尺度 Q8 的 completion 为 4–546（P50=46、P95=368），都按真实 EOG 停止。这组批量实验不测在线到达和排队延迟；原生接口没有逐请求时间，报告不推算延迟 P95。

### 校准效果

校准使用原始 BF16 和实际翻译模板、特殊 token、语料参考译文；实际收集 29×2048 token 的 imatrix，224 个投影矩阵有统计，共享 embedding/输出矩阵未加权。局部和全尺度候选复用同一矩阵。以下质量均为同样的 32 并发贪心输出；chrF++ / BLEU 越高越好：

| 权重 / KV | 混合语料 chrF++ | 英译中 BLEU | 中译英 BLEU |
| --- | ---: | ---: | ---: |
| 原 NVFP4 / F16 | 51.664 | 38.411 | 28.678 |
| OPUS 校准、局部搜索 / F16 | **52.346** | **39.866** | **29.871** |
| OPUS 校准、局部搜索 / Q8 | 52.354 | 39.697 | 29.553 |
| OPUS 校准、全尺度搜索 / F16 | 52.188 | 39.317 | 29.790 |
| OPUS 校准、全尺度搜索 / Q8 | 52.618 | 39.935 | 30.117 |

局部搜索 F16 相对原 NVFP4 增加 **0.682 chrF++ 分**，按目标语言分层的 1000 次配对 bootstrap 95% 区间为 `[+0.264, +1.178]`。全尺度 F16 增加 0.524，区间 `[-0.025, +0.993]`，且点估计低于局部搜索。因此当前默认模型采用**公开语料校准＋局部搜索**；全尺度搜索只作为离线研究方法保留。区间是该子集的探索性比较，未校正多重比较，也不代表生产质量保证。

## 历史：首次 NVFP4 校准与量化 KV 实验

| NVFP4 权重 / KV | 并发 | completion token/s | 512 条推理墙钟 | 峰值显存增量估计 |
| --- | ---: | ---: | ---: | ---: |
| 原 reference / F16 | 128 | 4736.53 | 7.029 s | 9.60 GiB |
| MSE + imatrix / F16 | 128 | 4772.27 | 6.968 s | 9.60 GiB |
| MSE + imatrix / Q8_0 | 128 | 4019.62 | 8.260 s | 6.03 GiB |
| MSE + imatrix / Q4_0 | 128 | 4075.00 | 8.118 s | 4.05 GiB |

| MSE + imatrix / F16 | 256 | 5045.95 | 6.600 s | 17.73 GiB |

权重优化保持了相近吞吐，不能把不足 1% 的差别认定为稳定加速。Q8 KV 在 256 并发下减少约 39% 的整任务峰值显存增量，但吞吐比同权重 F16 低约 12%；128 并发下低约 16%。Q4 同样有速度代价，未完成相对 BF16 的质量对照。Q8 提高到 256 并发也没有追平 F16 的 128 并发。因此本次没有证明 KV 量化能同时保持吞吐，默认仍为 F16。

显存是 `nvidia-smi memory.used` 每 100ms 采样的设备峰值，减去该进程启动前读数；包含初始化。桌面及其他驻留内容约占 12–13 GiB，这不是隔离的进程显存计数，也不是精确峰值。128 并发使用 ubatch 1024，256 使用 2048；跨并发不能归因为单个开关。历史 5386 token/s 来自不同发布构建与运行时状态，不与本表拼接计算加速比。24 次运行均完成全部 512 条，无错误、截断或空输出。

精度初筛使用原 64 条合成素材的前 32 条及 BF16 贪心伪译文校准，20 个 256-token chunk；模板文字未启用特殊 token 解析。后 32 条中的 4 条作为独立输入，固定 BF16 token 序列，以 `hy-logits --batch 1 --parallel 16` 对照。只统计 assistant 标记之后、预测译文及结束 token 的 262 个位置：

| 权重 / KV | 相对 BF16 的平均 KL，越低越近 | Top-1 一致率 |
| --- | ---: | ---: |
| 原 reference / F16 | 0.20529 | 89.69% |
| MSE，无校准 / F16 | 0.17684 | 87.40% |
| MSE + imatrix / F16 | 0.15135 | 90.84% |
| MSE + imatrix / Q8_0 | 0.13644 | 91.60% |

校准版 F16 的 KL 比旧权重低约 26%。这是四条样例的分布偏离指标，未测人工参考译文、BLEU、chrF 或 COMET；Q8 在这个小样本上的非单调改善不证明量化缓存普遍提高质量。各指标也不必同步改善，例如无校准 MSE 的 Top-1 一致率反而降低。本机保留了 logits 对照工具与原始 dumps，评分只覆盖译文预测位置。

验证还包括 77 项 Python 测试、`test-quantize-fns` 零失败、38 个补丁文件的干净恢复校验，以及 Q8 的批量启动、API 翻译、创建时间核对及管理停止。量化方法、实际命令及下一步优化见 [QUANTIZATION.md](QUANTIZATION.md)。

## 历史主对比：原版 Q4_K_M → 本项目 NVFP4

本次主对照直接比较**未修改的官方 llama.cpp** 与本项目完整部署方案。量化选择计入本项目的收益，不要求两端采用同一种四位格式。

RTX 5090 32 GB、Ryzen 7 9800X3D、Windows 11，NVIDIA 驱动 596.36。同一组 512 条请求、同样 256 并发、每条上下文 1024、batch/ubatch 2048、8 个推理 CPU 线程；每侧三次，每次启动全新进程，按“原版→本项目”的顺序交替执行，没有单独预热请求。

| 方案 | 量化 / 接口 | completion token/s 中位数 | 三次范围 | 推理墙钟中位数 |
| --- | --- | ---: | ---: | ---: |
| 官方原版 llama.cpp `b11029` | 腾讯 Q4_K_M / HTTP | 721.73 | 711.35–723.67 | 46.394 s |
| 本项目便携构建 | NVFP4 / 原生 JSONL | **5386.26** | 5133.05–5460.50 | **6.185 s** |

吞吐中位数比为 **7.463 倍（提高 646.3%）**，512 条墙钟减少 **86.7%**。本项目包含初始化的进程总时间中位数为 **7.463 秒**。六次运行均完成全部 512 条请求，错误、截断和空输出均为零；逐条 token 合计、结束状态和独立种子序列也已复核。

这是**量化、代码、调度、接口和构建共同作用下的整体方案比较**，不是纯源码或单一 CUDA kernel 的收益，也没有证明两种量化的译文相同或质量等效。原版三次实际输出为 33491 / 33553 / 33484 个 completion token，本项目三次均为 33314；时间比与 token 吞吐比因此略有不同。没有穷举原版所有并发与参数，不将这次相同并发对照称作原版的绝对最高性能。

公开证据：[逐次摘要与哈希](../benchmarks/upstream-comparison.json)、[原版发布来源](../benchmarks/upstream-release.json)。摘要没有本机路径、GPU UUID、PID 或逐条译文。

### 原版身份与模型证明

## 测量口径

素材为 [benchmark_cases.json](../scripts/benchmark_cases.json) 的 64 条固定翻译，重复 8 轮，共 512 条。跨轮原文重复；API 关闭 prompt cache，原生程序清空各波 KV，没有跨请求前缀共享。这不是翻译质量评测，也不覆盖所有文本长度与语言分布。

采样设置：temperature 0.7、top-p 0.6、top-k 20、repeat penalty 1.05、min-p 0，惩罚窗口 4096；每条请求独立种子为 `42 + 全局请求序号`。新对照两端均为并发 256、每条上下文 1024、batch/ubatch 2048、最大生成 512。

- **completion token/s**：真实生成 token 数除以墙钟，包含实际结束 EOG，排除填充 token；填充工作消耗的时间仍计入墙钟。
- **正文 token/s**：进一步排除 EOG。
- **原生推理墙钟**：包括输入读取、模板与分词、prefill、采样、decode、输出写入和首次图准备；排除模型及 context 初始化。
- **进程总时间**：从启动原生进程到退出，包含初始化。
- **HTTP 墙钟**：包含队列、请求、服务处理及首次推理，排除初始化和测量后的 JSONL 磁盘写入。新对照没有单独预热；下方早期历史 HTTP 记录使用过独立预热。
- **HTTP 含启动时间**：`loaded_process_wall_s` 在最后一条 HTTP 请求返回后截止，尚未停止服务、写出 JSONL，因此不能与原生进程启动到退出的总时间直接对比。

下表中的有效运行均完整完成 512 条，无错误、截断或空输出。正常结束不代表翻译语义完全正确。

## 历史记录：第二轮 GPU 批量采样前缀

以下为之前阶段的实验，使用历史本机 optimized 构建；保留作追溯，不作为 README 的原版主对照。27 次历史摘要见 [rtx5090-windows.json](../benchmarks/rtx5090-windows.json)。

相同 NVFP4、输入和生成参数，每项三次：

| 路径 | completion token/s 中位数 | 三次范围 | 推理墙钟中位数 |
| --- | ---: | ---: | ---: |
| 同轮 CPU 采样，4 线程 | 3758.46 | 3640.15–3770.44 | 8.864 s |
| GPU 批量前缀＋CPU 尾部，1 线程 | **5319.32** | 5129.73–5365.42 | **6.263 s** |
| GPU 批量前缀＋CPU 尾部，4 线程 | 5273.94 | 5201.73–5288.06 | 6.317 s |

1 线程方案较同轮 CPU 中位数提高 **41.5%**；正文吞吐中位数 5237.56 token/s，进程总时间中位数 7.485 秒。1 / 4 线程差距较小，没有证据表明 1 线程在所有负载上更快。

与首轮 NVFP4 的 3898.03 中位数相比，提高 **36.5%**。这是跨阶段历史比较，不是交错进行的严格成对试验。三组九次输出 JSONL 的 SHA-256 都与首轮 NVFP4 相同：

`30ba1cb6866957c0ff31f5790ce5760415a84cb33dcae3b0bed326875e551992`

此优化在 GPU 上批量执行惩罚、Top-K+1 和候选收集，保留 CPU 的 Top-P、温度、随机采样及独立 RNG；并列等异常行回退完整 CPU 链。代表性运行共处理 45824 行，39 行回退，候选及回退 logits 合计 D2H 约 26.5 MB；全词表逐行回传对应约 22.1 GB。这个约 834 倍是指定载荷的减少，未计历史 H2D 等其他传输，**不是吞吐加速倍数**。

GPU 批量前缀目前只用于专用文件程序，HTTP 服务未使用这条路径。

## 使用范围

固定波次适合大量独立请求。长短差异大时，已经结束的槽位会产生填充工作；GPU 前缀尾波保留完整宽度，因此输入只有少数尾项时不一定优于 CPU 尾波缩宽。实验性的连续补位未取得吞吐优势，未设为默认，也不支持与 GPU 前缀组合。

显存配置直接影响速度。FP16 KV 在 256 并发、上下文 1024 时约占 16 GiB；盲目扩大上下文可能触发 Windows 共享内存，明显拖慢推理。查看 [自动配置和手动起点](USAGE.md#显存与长文本)、[实测显存摘要](../benchmarks/rtx5090-vram.json)。

源码改动与数值验证范围见 [优化说明](OPTIMIZATIONS.md)。没有用合成 decode 峰值替代真实翻译吞吐，没有宣称量化无损或已获得正式 COMET/BLEU 质量结论。

## 复现原版对照

先完成模型安装并停止其他 GPU 工作负载。以下是 RTX 5090 大显存配置，脚本不自动降低并发；显存较少时应调整尺寸。

1. 下载上面链接的官方 `b11029` Windows CUDA 13.4 程序 ZIP，解压到 `.local/upstream-benchmark-bin`，其中应直接包含 `llama-server.exe`。记录资产 SHA 和 `--version`。
2. 将上面固定版本的腾讯原始 Q4_K_M 下载为 `.local/upstream-benchmark-models/Hy-MT2-1.8B-Q4_K_M.gguf`，校验其 SHA。也可按 [源码准备](BUILD.md) 获得 gguf-py 和开发 Python，再用 `unpack_hymt_gguf.py` 从本项目 Q4_K_M 恢复；无需重新量化。
3. 下载本项目 NVFP4，运行三对比较：

```powershell
.\setup-model.cmd --profile fast
.\stop-server.cmd
.\scripts\run-python.cmd scripts\benchmark_upstream.py --stock-dir .local/upstream-benchmark-bin --stock-model .local/upstream-benchmark-models/Hy-MT2-1.8B-Q4_K_M.gguf --optimized-model models/Hy-MT2-1.8B-NVFP4-fused.gguf --quantization Q4_K_M --optimized-quantization NVFP4 --parallel 256 --repeats 3 --rounds 8 --label my-q4-to-nvfp4
.\scripts\run-python.cmd scripts\summarize_upstream_benchmark.py --report results/my-q4-to-nvfp4/report.json --output results/my-upstream-summary.json
```

实验每轮启动原版服务，测量后关闭，再启动本项目原生进程。更换 `--label` 才能重新运行，避免覆盖原记录。`report.json` 保存版本、模型及二进制 SHA、参数和逐次数据；脱敏脚本只输出白名单证据，并拒绝未完成的重复测量。完整报告含译文和本机信息，不应直接提交 Git。

复现历史原生开关实验可使用 `scripts/run_native_experiment.py`；显式指定 `--binary bin/hy-batch.exe --context 1024 --parallel 256 --ubatch 2048`。不同驱动、构建、系统状态、语言和文本长度都会影响绝对速度，应保留全部运行，不能只选最快的一次。
